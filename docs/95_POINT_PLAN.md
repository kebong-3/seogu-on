# 서구온 95점 목표: 구현·실증·제출 계획

## 1. 제출에서 설명할 중심 가치

서구온의 중심 사례는 **생활권 공공공간의 운영조건을 비교하고 후속 확인으로 갱신하는 소규모 업무 디지털트윈**으로 잡는다. 담당자가 실제 공간을 선택하고, 확인한 운영시간과 변경 가정을 같은 조건에서 비교한 뒤, 협의·현장 확인 결과를 다시 입력하여 다음 검토를 갱신하는 업무다.

제출용 핵심 설명은 다음과 같이 구성할 수 있다.

> 서구온은 공개자료에 수록된 실제 공간의 위치와 고유 식별자에 담당자의 확인 기록을 연결합니다. 생활권에서 사용할 공공공간을 같은 요일·시간에 비교하고, 개방시간을 바꾸는 대안의 차이와 미확인 사항을 보여 줍니다. 담당자가 후속 확인을 입력하면 다음 계산이 바뀌고 이전 검토도 보존됩니다. AI는 계산 결과를 바탕으로 차이의 이유와 부서 간 협의 질문을 정리하며, 판단과 사용 승인은 담당자가 맡습니다.

‘디지털트윈’의 근거는 3D 화면의 유무나 연결한 API의 개수보다 **현실 공간 ID → 시점이 있는 상태 → 변경 가정의 재계산 → 현장 피드백**의 연결에 둔다. 현재 범위에서는 실제 객체와 확인 상태를 다루는 업무 모델이라고 설명한다. 센서로 자동 갱신되는 도시 전체 실시간 트윈, 이용 수요 예측 모델, 정책 편익의 실측 모델이라는 표현은 사용하지 않는다. 구현 범위와 계산 의미는 [공공공간 모델 명세](SPACE_TWIN_MODEL.md), [공통 계산 코드](../shared/space-twin-model.js)에 정리되어 있다.

## 2. 평가 배점별 95점 목표 설계

자유주제 평가 배점은 필요성 20점, 창의성 30점, 활용성 20점, 완성도 15점, 확산가능성 15점으로 놓는다. 아래는 **95점에 도전하기 위한 증거 배분**이며 현재 점수, 예상 수상 점수 또는 심사 결과가 아니다. 최종 자체평가는 실제 배포·화면 검증과 실증 결과를 확보한 뒤 따로 작성한다.

| 평가 항목 | 배점 / 목표 | 제출에서 입증할 주장 | 목표를 뒷받침할 최종 증거 |
|---|---:|---|---|
| 필요성 | 20 / **19** | 자료 찾기·운영 확인·대안 비교·협의안 작성이 반복되는 실제 행정 문제를 다룸 | 담당 부서의 구체적 업무 사례, 기존 처리 과정, 불편·누락 사례, 동일 과제의 실측 기준선 |
| 창의성 | 30 / **28** | 지도에 확인 상태·가정·결과·후속 기록을 연결해 행정 판단을 반복 갱신함 | 현실 공간 ID에 연결된 전후 시연, 미확인과 0의 분리, 출처·가정별 행, AI의 설명·협의 질문이 업무 판단에 기여한 사례 |
| 활용성 | 20 / **19** | 공무원이 기존 방식보다 수월하고 정확하게 대표 과제를 완료함 | 실제 담당자의 기존 방식/서구온 짝 비교, 처리시간·오류·출처 누락 원기록, 사용 후 개선 요청과 반영 이력 |
| 완성도 | 15 / **15** | 계산·화면·기록·복구·장애 대체가 실제 배포에서 연결되어 동작함 | 최종 빌드와 배포 식별자, 화면 가독성·키보드·모바일 검사, 백업 복구·만료·오류·AI 장애 검증, 운영 담당자와 점검 계획 |
| 확산가능성 | 15 / **14** | 지역 자료와 설정을 교체하여 동일 업무 흐름을 재사용함 | 실제 두 번째 지자체 자료 패키지, 코드·출처·좌표 검사, 해당 지역의 동일 시연, 실제 모델 두 종 실행 기록, 적용 비용·잔여 어댑터 목록 |
| 합계 | **100 / 95** | 구현과 현장 증거가 함께 갖춰진 상태를 목표로 함 | 미완료 증거는 제출물에서 계획으로 표시 |

목표 배점만 채워 자체 점수를 선언하지 않는다. 특히 실제 담당자의 효과 측정, 실제 다른 지역 적용, 실제 모델 두 종 호출과 운영 책임체계가 빠져 있다면 해당 한계를 그대로 남긴다. 프로그램 시험의 통과 건수로 행정 성과나 외부 확산 성과를 대체하지 않는다.

## 4. 대표 행정 업무를 좁혀 완성하기

### 대표 사례: 주민 모임·돌봄·학습을 위한 저녁 공공공간 검토

회의실·강당 등 공개된 공간 중 어느 곳을 특정 요일 저녁에 활용할지 검토한다. 공간을 늘리는 사업에 앞서 기존 공간의 시간을 조정하는 선택지를 함께 살핀다. 담당자는 공공공간 관리 부서, 동 행정복지센터, 주민자치·평생교육·돌봄 관련 부서 중 실제 수요가 있는 업무 주체로 정한다.

업무 순서는 다음과 같다.

1. 검토 목적·시간대·생활권을 정하고 실제 공간을 지도에서 선택한다.
2. 원자료와 현재 운영조건이 다른지 담당자가 확인한다. 운영 여부를 모르면 미확인으로 둔다.
3. ‘현재 운영 유지’, ‘일부 공간 저녁 개방’, ‘다른 공간으로 분산’과 같이 현실적인 대안을 입력한다. 비용이 없으면 미산정으로 남긴다.
4. 같은 조건의 충족 공간 수·겹치는 시간·미확인 수와 입력한 추가 운영비를 비교한다.
5. AI가 정리한 차이의 이유와 확인 질문을 검토하여 관리 부서에 협의한다. 자동 최적안 선정으로 해석하지 않는다.
6. 협의 후 실제로 확인한 조건을 현황 기록에 반영하고 재계산한다. 스냅샷에는 이전 검토를 남긴다.

이 흐름은 재난 시 공간 활용에도 쓸 수 있지만 평소 주민 모임·학습·돌봄·마을의제 논의의 장소 검토를 대표 사례로 보여 주면 활용 범위가 자연스럽게 전달된다. 도시설계 전체를 자동 결정하는 기능이라고 설명할 필요는 없다. 입지·공간 활용의 초기 검토와 부서 협의에 필요한 근거를 모으는 범위가 분명하다.

AI가 없어도 숫자 계산과 기록 갱신은 가능해야 한다. AI의 추가 가치는 숫자를 다시 말하는 것에서 끝나지 않고 ‘왜 이 대안만 해당 요일에 가능해지는가’, ‘운영 인력·예약·사용 승인을 누구에게 무엇부터 확인해야 하는가’, ‘현재 미확인 때문에 어떤 결론을 보류해야 하는가’를 짧은 검토 의견으로 정리하는 데 있다. 근거가 없는 수요나 주민 선호를 채우지 않는다. [AI 서버의 근거 구성](../server/ai/space-review.js)

## 5. 95점 목표를 위한 후속 실행 조건

### A. 실제 담당자의 업무효과 짝 비교

**할 일:** 기존 방식과 서구온을 같은 사람이 수행하는 짝 비교를 실시한다. 예비 실증은 실제 담당자 6~10명, 두 종류 대표 과제를 목표로 하되 기관 여건에 맞춰 확정한다. 인원은 연구로 입증된 충분 표본이 아니라 실행 가능한 초기 모집 계획이다.

- 과제 1: 주어진 시간대에 사용할 공공공간과 두 개 변경안을 검토하고 출처가 있는 의견서를 작성한다.
- 과제 2: 일부 운영조건이 바뀐 자료를 받아 영향 범위를 다시 계산하고 이전 의견을 수정한다.
- 방식 순서는 기존→서구온과 서구온→기존을 균형 있게 배정한다. 학습·기억 효과를 줄이도록 난이도를 맞춘 과제 세트와 자료 버전을 고정하고 배정표를 보관한다.
- 시작/완료 시각, 계산 오류, 출처 누락, 결과물, 중단·보류 사유를 기록한다. 확인하지 않은 오류 수를 0으로 넣지 않는다.
- 정답과 채점 기준을 사전에 고정하고, 가능하면 수행 방식을 모르는 검토자가 결과물을 확인한다.

**완료 조건:** 같은 과제·조건에서 각 방식이 모두 완료된 개인별 기록, 양쪽 결과물, 수행 순서와 제외 사유가 남아 있고 각 과제에 실제 참가자 6명 이상의 완성된 짝을 확보한다. 이는 본 계획의 예비 실증 조건이며 통계적 일반화를 보장하는 기준은 아니다. 결과는 개인별 시간 차이·오류 차이·출처 누락 차이와 중앙값, 표본 수를 함께 공개한다. 개선이 없거나 시간이 늘어난 사례도 남긴다. 단순히 빨라졌지만 오류가 늘었다면 ‘행정효율 향상’으로 결론내리지 않는다. [측정·이력 코드](../shared/pilot-measure.js)

**제출 증거:** 익명 원기록 CSV/JSON, 과제지·채점표, 결과물 전후 예시, 소규모 관찰의 한계, 피드백을 반영한 변경 내역. ‘업무시간 30% 절감’처럼 측정하지 않은 성과 수치는 넣지 않는다.

### B. 실제 두 번째 지자체의 자료로 같은 업무 실행

**할 일:** 실제 대상 지자체를 정하고 출처와 이용 조건이 확인되는 경계·공공공간 자료를 수집한다. 지역명만 바꾸지 않고 코드 체계·좌표·원자료 ID·기준일을 매핑한다. 기존 서구 전용 API가 새 지역을 조회하는 것처럼 노출되지 않게 기능별 범위를 점검한다. [지역 적용 절차](REGION_ADOPTION.md)

**완료 조건:** `sample:false`인 실제 자료 패키지가 구조 검사를 통과하고, 해당 지역의 공간 위치·이름·행정구역을 표본 확인하며, 담당자 확인→대안 비교→후속 확인→백업 복구까지 동일 흐름을 실행한다. 자료의 수록 범위와 누락 여부를 명시하고 검증 중 발견된 코드·좌표·출처 문제를 기록한다. 실제 해당 지역 담당자가 최소 한 차례 결과를 검토한다.

**제출 증거:** 지역 프로필, 원자료 링크·수집일·변환 기록, 검증 결과, 실제 두 번째 지역의 화면·검토 결과, 전환에 든 작업시간, 추가로 연결해야 할 API 목록. 합성 시험 자료를 실증 지자체로 소개하지 않는다. [현재 합성 시험](../tests/region-profile.test.mjs)

### C. 실제 모델 두 종으로 실행 기록 확보

**할 일:** 서버가 다시 계산한 동일 근거 묶음과 같은 설명 요청을 서로 다른 실제 모델 두 종에 보내 품질과 실패 대응을 비교한다. 특정 정부 공통기반이나 기관 모델에서 직접 실행하지 않았다면 해당 환경 호환 완료라고 적지 않는다.

**완료 조건:** 각 모델의 실제 제공기관·모델 식별자·호출일·응답 원문·지연·실패 상태를 기록한다. 미확인, 기한 만료, 부분 개방, 운영 중단, 미산정 비용, 여러 대안 등 최소 8~12개 서로 다른 사례를 같은 조건에서 확인한다. 이 사례 수는 제출용 초기 검사 계획이며 품질 인증 기준은 아니다. 숫자·대안명·가정 여부의 오인, 근거 없는 효과 주장, 필요한 협의 질문을 사람이 검토한다. AI 실패 시 계산 결과와 규칙 설명이 남는지도 확인한다.

**제출 증거:** 비밀키가 없는 실행 명세와 로그, 사례별 검토표, 잘못된 응답의 처리 사례, 모델을 바꾸어도 동일한 계산 결과가 유지되는 비교. 모의 테스트와 실제 API 호출을 별도 표로 구분한다. [호환 경로 시험](../tests/model-portability.test.mjs), [공공공간 AI 시험](../tests/space-review.test.mjs)

### D. 배포·가독성·복구 QA 완료

**할 일:** 최종 빌드로 실제 배포에서 지도 진입, 공공공간 선택, 현장 기록, 대안 비교, AI 설명, 스냅샷, 보고서·백업을 연속 수행한다. 실제 브라우저의 텍스트·선택 상태·입력 배경·오류 메시지 대비와 작은 화면의 잘림을 점검한다. 사용자 요청의 ‘글씨가 잘 보이지 않는 문제’를 별도 합격 항목으로 둔다.

**완료 조건:** 대표 데스크톱·모바일 화면에서 내용이 읽히고 주요 동작이 키보드로 가능하며 포커스 위치를 확인할 수 있다. 조건 변경 후 오래된 결과를 새 결과로 저장하지 않는다. 깨진 백업·다른 지역 백업·충돌 기록·저장 실패 시 기존 기록을 보존한다. 새로고침·재진입·백업 가져오기·AI 장애에서도 가정과 확인값 구분을 유지한다.

**제출 증거:** 배포 식별자·확인 일시·브라우저/화면 조건·완료 체크표, 전후 화면, 확인한 한계와 남은 결함. 이 문서의 작성 시점에는 새 버전의 최종 Production/UI QA 결과가 아직 없으며 이후 실제 기록으로 채워야 한다.

### E. 운영 책임과 자료 갱신 절차 확정

**할 일:** 자료 관리자, 공간별 확인 담당자, AI 의견 검토자, 오류 접수·복구 담당자를 지정하고 갱신 주기와 만료 처리 기준을 합의한다. 기관 운영 시 필요한 공유 저장·권한·승인·감사·백업 범위를 정한다.

**완료 조건:** 원자료 변경 시 ID·좌표·기준일을 검사하는 절차, 미확인·만료 자료의 재확인 절차, 담당자 변경 시 인수인계, 백업 복구 책임과 실행 기록이 있다. 브라우저 기록만 사용하는 시범 운영과 기관 공동 운영의 범위를 명확히 구분한다. 검토 보고서에 가정·출처·확인일·미확인 항목이 남는다. [운영 한계와 갱신 안내](REGION_ADOPTION.md), [기록 명세](SPACE_TWIN_MODEL.md)

**제출 증거:** 한 장짜리 운영 역할표, 자료 갱신·오류 처리 사례, 백업 복구 확인, 후속 개발 범위와 책임자. 실제 운영체계가 없다면 ‘기관에서 운영 중’으로 표현하지 않는다.

## 6. A4 3~5쪽 제출서 권장 구성

분량은 공고 양식이 있으면 그 양식을 우선한다. 아래는 제한된 분량에 필요한 근거를 모으는 구성이다.

| 쪽 | 내용 | 넣을 증거 |
|---|---|---|
| 1쪽 | 행정 문제와 사용 주체, 대표 업무, 도입 목적 | 실제 업무 흐름·불편 사례·한 문장 서비스 정의 |
| 2쪽 | 현실 객체–상태–가정–피드백의 작동 방식 | 같은 공간의 전후 화면, 출처·확인·가정 구분, 미확인 처리 |
| 3쪽 | 실제 활용과 효과 | 짝 비교 원기록에 근거한 표, 표본·순서·오류·출처 누락, 개선 요청과 반영 |
| 4쪽 | 완성도와 확산 | 실제 두 번째 지역, 모델 두 종 실행, 배포·복구 QA, 적용 절차 |
| 5쪽 | 운영·한계·후속 계획 | 담당자·갱신 주기, 구현/미검증 구분, 코드·영상·자료 링크 |

3쪽으로 제한되면 1~2쪽의 설명을 줄여 첫 쪽에 묶고, 두 번째 쪽에 실제 업무효과, 세 번째 쪽에 완성도·확산·운영을 배치한다. 본문은 기능 목록보다 하나의 업무가 어떻게 완료되고 수정되는지를 보여 준다. 3D 화면이나 API 목록은 필요한 경우만 보조로 넣는다.

실증 결과가 아직 없으면 3쪽의 효과 표를 꾸며 넣지 않는다. 실제 구현·시험 결과와 예정된 실증 계획을 명확히 분리한다. 95점은 증거를 갖추기 위한 목표로만 표시한다.

## 7. 5분 시연 권장안

| 시간 | 보여 줄 동작 | 심사자가 확인할 핵심 |
|---|---|---|
| 0:00~0:40 | 저녁 주민 활동 공간이라는 구체적 업무 제시, 실제 공간 선택 | 누구의 어떤 업무를 돕는가 |
| 0:40~1:30 | 원자료·미확인 표시와 현장 확인 기록 | 공개된 운영 문장을 현재 확정값으로 사용하지 않는가 |
| 1:30~2:30 | 두 개 대안을 같은 시간조건으로 계산 | 조건 충족·부분 개방·미확인·미산정 비용이 분리되는가 |
| 2:30~3:10 | AI 설명과 부서 협의 질문, 계산 근거 표시 | AI가 행정 검토에 기여하며 근거 밖 결론을 만들지 않는가 |
| 3:10~4:10 | 후속 확인값 수정, 재계산, 이전 스냅샷과 비교 | 현실 상태의 피드백이 실제로 다음 계산을 바꾸는가 |
| 4:10~4:40 | 백업/보고서와 실제 두 번째 지역 적용 증거 | 기록을 전달·복원하고 같은 흐름을 재사용하는가 |
| 4:40~5:00 | 실측 효과와 아직 남은 한계 | 구현·실증·계획을 정직하게 구분하는가 |

시연용으로 작성한 운영시간은 **시연 가정**이라고 표시한다. 실제로 조사하지 않은 상태를 현장 확인으로 저장해 제시하지 않는다. 현장 기록 입력 기능을 보여 줄 때도 ‘시험용 입력, 실제 조사 아님’이라고 근거에 적고 운영 기록과 분리한다. 타 지자체 실증이나 실측 효과가 아직 없다면 해당 구간에는 실제 검증된 재사용 구조와 앞으로의 실행 조건을 보여 준다. 준비되지 않은 증거를 완료 성과처럼 대신 설명하지 않는다.
