# 서구온 디지털트윈 API·업무 확장 기획

검토일: 2026-10-25. 기준 구현: 0.12.2 소스와 자료 설명서. 이 문서는 후속 개발 기획이며 아래 추가 기능의 구현·운영 수신 완료를 뜻하지 않는다. 외부 서비스의 명세·요금·승인 조건은 본 검토일 공개 공식 페이지로 확인했다.

## 1. 가장 먼저 달라져야 할 것

주민이 궁금한 것은 ‘시설이 지도에 몇 개 있는가’보다 **내 조건과 시각에 이용할 수 있고, 실제로 찾아갈 수 있는가**이다. 담당자가 궁금한 것은 **상황이 바뀌었을 때 어느 시설·접근로·안내부터 바꿔야 하는가**이다.

따라서 API는 다음 연결 중 하나를 완성할 때 붙인다.

1. 시설의 공시 정보 → 이용대상·운영조건 확인 → 실제 이동거리 → 이용 후보 안내.
2. 날씨·시설 상태 변경 → 기존안/변경안 재계산 → 현장확인·운영조정 → 주민 안내 변경.
3. 고장·휴관·통제 확인 → 관련 시설/동선의 영향 확인 → 조치·재확인 → 변경 전후 이력.

**대표업무는 4개로 제한한다.** 지역별로 같은 업무를 재사용하며, API마다 별도 메뉴를 늘리지 않는다. 이 기획의 우선순위와 도입 순서는 제품 판단이다.

## 3. 우선순위별 대표업무

### 우선 1 — 내 시간·대상에 맞는 돌봄·생활시설 찾기

**주민의 갈림길:** ‘가까운 A’와 ‘조금 멀지만 내 연령·시간 조건에 맞는 B’ 중 어느 시설에 먼저 문의할까?

**행정의 갈림길:** 운영시간 연장, 기존 공공공간 연계, 신규 거점 검토 중 어느 대안을 먼저 협의할까?

- 현재 기반: 어린이집 공개현황, 개방 공공공간, 학교·정류장 대표위치.
- 추가 입력: 시설별 이용대상·휴관/운영시간·공개 예약 연결, 대표좌표와 구분한 출입구, 보행경로. 초등돌봄·유치원·영유아 보육은 대상과 제도를 구분한다.
- 추가 API/신청: 어린이집정보공개포털 별도 API 신청·승인과 발급키, 보행경로 공급자 앱 키. 행정계획용 연령별 인구는 SGIS 별도 인증정보가 필요하다.
- 변화 시나리오: ‘A시설 오늘 임시휴관’ 또는 ‘B시설 평일 19→21시 개방’을 확인/가정으로 바꾼다. 같은 출발위치·연령·시각으로 후보와 이동거리의 변화를 재계산한다.
- 주민 출력: 이용조건 충족/기관 확인 필요를 구분한 후보, 도보 예상거리·시간과 경로 출처, 기관 연락·예약 원문 링크, 마지막 확인시각.
- 행정 출력: 운영 연장/공간 연계 전후 이용조건을 충족하는 검토 출발지 수, 추가 현장확인 목록, 담당자 협의 메모. 실제 주민 수는 적절한 통계·방법을 검증한 뒤 별도 표시한다.
- 완료 기준: 담당자가 확인한 대상·시간 조건과 앱 결과가 일치하고, 실제 출입구 간 보행경로를 표본 현장 대조한다. 휴관 변경이 해당 시설 추천에서 제외되며 과거 결과는 당시 상태로 남는다.

**입소 빈자리를 첫 목표로 삼지 않는다.** 공시 정원−현원은 연령별 반·모집·자격·현시점의 입소 가능성을 보장하지 않는다. 공개 API에 없는 실시간 가용성은 해당 기관의 협력 또는 공식 예약 연계가 있어야 제공한다.

### 우선 2 — 오늘 폭염에 어느 시설을 열고 어디를 보완할까

**주민의 갈림길:** 목적지까지 그대로 이동할까, 확인된 개방 쉼터를 경유할까?

**행정의 갈림길:** 새 그늘막을 설치할까, 기존 실내공간 운영시간을 늘릴까, 대기 위치를 바꿀까?

- 현재 기반: 기상 조회 코드, 정류장·그늘막·쉼터 위치, 일부 그림자 표현과 위치 비교.
- 추가 입력: 기상청 시각별 예보·공식 특보, 실제 정류장 대기위치, 쉼터 개방시간·임시휴관, 수목·그늘막·건물 높이와 시간별 그늘 검증.
- 추가 API/키: 기존 기상청 서비스 활용승인·키를 우선 재사용한다. 쉼터 원자료의 현재 수신을 검증하고, 시간별 개방 상태는 관리기관 확인자료를 결합한다. 보행경로는 우선 1과 공통 사용한다.
- 변화 시나리오: 평일 18시 폐쇄인 실내공간을 21시까지 연다고 가정하거나, 그늘막 추가/대기위치 이동을 비교한다. 특정 시각에 개방된 쉼터까지 접근 가능한 검토 출발점과 직접 일사 노출 위치의 변화를 표시한다.
- 주민 출력: 발표시각이 있는 공식 날씨·특보, 그 시각 개방 확인된 쉼터, 기관 연락과 이동경로. 도로변 미기후를 실측한 것처럼 표현하지 않는다.
- 행정 출력: 시간별 운영 연장 대상, 대기위치별 현장확인표, 기존시설 활용안/설치안 비교서와 비용 입력란.
- 완료 기준: 현장 확인한 쉼터 시각조건과 지도 일치, 대표시각 그늘의 현장 대조, 개방·미확인·휴관 구분. 온도 저감·건강효과는 검증 모델/측정 없이는 산정하지 않는다.

### 우선 3 — 비가 올 때 어느 접근로와 시설부터 확인할까

**주민의 갈림길:** 확인된 통제 구간을 지나는가, 현재 확인된 대체 접근로가 있는가?

**행정의 갈림길:** 어느 지하차도·하천변 진입로·취약시설을 먼저 확인하고 어느 시설에 연락할까?

- 현재 기반: 기상·ITS 돌발 코드, 과거 침수 이력과 공개 시설 위치. 현재 통제·안전한 우회 경로는 미구현.
- 추가 입력: 실시간 강우/수위·홍수특보, 최신 도로 통제·해제, 담당자가 확인한 하천 산책로/지하차도 진입구와 차단 구간, 시설 연락처. 하천 수위와 해당 도로 침수는 별개의 사실이다.
- 추가 API/키: 한강홍수통제소 표준수문DB의 별도 인증키, 국토교통부 재난상황정보의 ITS 공식 신청·규격 확인. 광주·순천의 해당 관측소·도로 제공범위를 실제 응답으로 먼저 검증한다.
- 변화 시나리오: 확인된 통제 구간 하나를 차단/해제하거나 시설 휴관을 반영해 접근 가능한 검토 출발점과 안내가 어떻게 바뀌는지 재계산한다. 임계수위·통제 기준은 승인된 지역 운영기준을 별도 등록한다.
- 주민 출력: 공식 통제 위치·기관·시각, 확인된 통제 해제/미확인 상태, 공식 안내 원문. 경로망·차단 반영·현장 대조가 완료되기 전에는 자동 ‘안전 우회길’을 제공하지 않는다.
- 행정 출력: 통제·미확인 접근로에 연결된 수록 시설과 연락목록, 점검·통제 확인표, 변경 전후 기록.
- 완료 기준: ‘과거 침수 이력’, ‘가정된 위험지도’, ‘현재 관측’, ‘확인된 통제’를 화면·범례·보고서에서 구분한다. 통제의 신규/해제를 재현하고 누락·지연 때 정상통행으로 바꾸지 않는다.

### 우선 4 — 고장·휴관 확인을 지도와 업무완료에 연결하기

**주민의 갈림길:** 위치만 존재하는 시설인가, 최근 이용·작동을 확인한 시설인가?

**행정의 갈림길:** 새 시설이 필요한가, 기존 시설을 수리/개방하는 것으로 해결되는가?

- 현재 기반: 안전시설·돌봄시설 위치, 일부 현장기록. 조직 공용 상태·조치 관리와 주민 공개 연동은 미구현.
- 추가 입력: 관리 자산ID, 확인시각·확인방법, 고장/휴관/정상 상태, 처리담당·기한·조치결과·재확인. 주민 제보와 담당자 확인을 분리한다.
- 추가 API/키: 외부 API보다 관리기관의 현장 확인자료 연결과 공유 저장이 우선이다. IoT/시설관리시스템은 실제 연계권한·자산ID·상태값이 제공되는 시설부터 선택한다.
- 변화 시나리오: 비상벨 고장→임시 안내→수리→작동 재확인, 쉼터 임시휴관→대체 개방을 기록하고 지도/추천/점검목록을 다시 계산한다.
- 주민 출력: 공개 가능한 이용 상태·확인시각·문의처. 신고자·아동·상담/피해자 정보와 비공개 보호시설 위치는 제외한다.
- 행정 출력: 중복 제보를 자산별로 묶은 작업목록, 미처리·재확인 기한, 수리/신설 대안, 과거 상태의 보고서 재발행.
- 완료 기준: 기관 공용 상태가 다른 기기에서도 같고, 확인되지 않은 주민 제보가 즉시 확정사실이 되지 않는다. 조치완료와 실제 재확인을 별도 기록한다.

## 4. 추가 서비스의 공식 확인과 도입조건

아래 ‘필요정보’는 신청·연결 준비사항이다. 환경변수 이름을 새로 나열하거나 키 발급만으로 구현이 완료된다고 안내하지 않는다. 해당 서비스가 전국형이어도 실제 지역·유형·시점 제공범위를 응답으로 검증한다.

| 도입 역할 | 공식 서비스·명세 확인 | 필요한 인증·비용·조건 | 개발 전 확인할 항목 |

## 5. 개발 순서와 ‘붙일 가치’ 판단

| 단계 | 구현할 수 있는 구체적 결과 | 먼저 확보할 것 | 다음 단계로 넘어갈 조건 |
|---|---|---|---|
| A: 기존자료로 업무 완결 | 시설 하나 선택 → 주변 시설/출처 → 담당자 확인표 → 보완안 → 검토서 | 현재 자료와 실제 담당자의 한 과제 | 설명 없이 처음 사용자가 끝까지 완료. 기존 방식 대비 시간·누락·오해를 측정 |
| B: 대상·시각·실제 접근 | 내 조건에 맞는 시설 후보와 보행 경로, 휴관 시 후보 변화 | 출입구·운영/자격 확인 + 보행 API, 어린이집 상시갱신 | 시설 조건 표본 대조, 보행경로 현장 대조, 실패/결측 처리 |
| C: 현실 상태 갱신 | 고장·휴관 → 담당 확인 → 조치 → 재확인이 주민 안내/행정목록에 반영 | 기관 공용 상태 저장·운영 담당·변경 이력 | 다른 기기 일치, 확인책임과 공개범위, 이전 보고서 재현 |
| D: 수요·운영 대안 검토 | 같은 인구·조건·시점으로 운영 연장/기존공간 활용/시설 추가를 비교 | SGIS·실제 이용/문의수요·비용 입력, 비교방법 | 연령/기준연도/중복/부분집계·가정 검증, 실제 담당자의 판단에 도움 확인 |
| E: 기상·통제 대응 | 날씨·수위·확인된 통제 변경이 대상시설·접근성·안내를 갱신 | 기상·홍수·ITS 실제 지역 응답과 현장 통제 관리 | 통제·해제 재현, 지연·중단 대응, 현장/공식 안내와 대조 |

주민 실용성은 **B**, 디지털트윈으로서의 지속성은 **C**, 시설 정책검토는 **D**가 핵심이다. 폭염은 기존 자료가 많아 B/C를 먼저 적용하기 좋다. 폭우 우회는 필요한 통제·보행망의 제공범위가 검증된 구간부터 E로 제한한다.

## 6. 지금 사용자에게 요청할 준비사항

1. **보행경로 공급자 앱 키와 선택 요금제**: 우선 소수 시설의 출입구 간 경로를 검증한다. 무료 한도 안에서 실패 시 차단하도록 설계하고 운영 사용량을 별도 확인한다.
2. **SGIS 서비스 ID·보안 Key**: 행정계획용 인구 배경정보를 붙일 때 사용한다. 기본 시설조회·운영시간 필터를 SGIS 발급 때문에 막을 필요는 없다.
3. **어린이집정보공개포털 별도 API 승인·키**: 공시정보 갱신용이다. 실제 운영시간·자격·모집은 응답 필드를 확인한 뒤 부족한 항목의 공식 자료를 별도 확보한다.
4. **기존 기상청/ITS 활용승인·운영 수신 확인**: 이미 있는 연결부터 점검한다. 새 재난상황정보는 별도 신청·명세 검토 대상으로 표시한다.
5. **홍수통제소 키와 지역 관측소·통제 담당 자료**: 호우 기능을 확장할 때 확보한다. 모든 API를 한 번에 신청하지 않아도 된다.
6. **시설 5~10곳의 실제 운영·출입구·관리자 확인표**: API 키보다 먼저 쓸모를 검증할 수 있는 최소 현장자료다. 아동·이용자 개인자료는 필요 없다.

키는 서버 설정에 보관한다. 신청서·키·비공개 운영정보가 저장소나 주민 화면에 노출되지 않도록 하고, 실제 수신·갱신 성공을 확인한 서비스만 연결 완료로 표시한다.

## 7. 보류할 확장

- 전국 공통처럼 보이지만 특정 도시/장소만 제공하는 실시간 혼잡도: 서구·순천의 제공범위와 비용이 확인되기 전에는 도입하지 않는다.
- 공개 CCTV의 단순 개수를 여성 안전점수로 환산: 설치목적·관제·현장 시야가 달라 비교근거가 되지 않는다.
- 건물 대표좌표 간 직선거리로 유모차·휠체어·안전귀가 길 안내: 실제 도로·입구·단차·통제 확인이 먼저다.
- 많은 겹침 레이어와 API 메뉴: 같은 주민질문/행정판단을 바꾸지 못하는 자료는 우선순위에서 내린다.

## 8. 조사 경로와 확인수준

사용자가 알려 준 [공공데이터 API 검색 사이트](https://public.rimikimi.com/)는 후보 탐색에 사용했다. 열람 당시 2026-10-19 갱신 표기를 확인했다. 신청·기술·제공범위·요금 판단은 위 표의 공식 원천으로 다시 확인했다.

본 작업은 공개 명세·현재 소스의 비교와 기획 문서 작성이다. 새 인증키 발급, 실제 키 호출, API 연결 개발, 실증 효과 측정은 수행하지 않았다. 홍수통제소·ITS 일부 직접 페이지는 timeout이 있어 공식 검색본문과 공공데이터포털 설명으로 후보를 확인한 수준이며, 미확인 요청·응답 항목을 구현된 계약으로 정하지 않았다.
