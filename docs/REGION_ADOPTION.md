# 타 지자체 적용 안내

## 1. 지금 재사용할 수 있는 범위

서구온은 **지역 프로필 + 행정경계 + 공공공간 자료**를 바꾸어 같은 공공공간 검토 흐름을 다른 지역에서 사용할 수 있게 구성했다. 경계 위에 시설의 위치와 확인된 상태를 겹쳐 보고, 공간 운영 시나리오를 비교하고, 계산 결과를 바탕으로 검토 의견을 만드는 흐름이다. 데이터 수집 대상 지역이 달라도 이 흐름의 화면·검증·계산 코드는 공유한다.

현재 실제 선택 지역은 **전남광주통합특별시 서구와 순천시**다. 메뉴의 **다른 지역도 적용해보기**에서 순천을 선택하면 실제 순천 경계·공공공간으로 이동한다. 같은 공공공간 조회, 현장 확인 기록, 운영 대안 비교, 계산 결과 설명 흐름을 사용한다. 순천은 별도로 합성한 공간이나 서구 좌표에 이름을 바꾼 자료가 아니다.

기존 재난·교통·기상·생활 자료와 일부 도구에는 서구 전용 제공기관 호출·지역코드·레이어가 남아 있다. 순천 프로필은 `legacySeoguServices: false`로 구분하고 해당 서비스를 비활성화한다. 순천의 지도 질의는 순천 공공공간 자료에 근거하는 별도 조회 경로를 사용한다. 다른 분야까지 확장하려면 제공기관별 지역 매개변수와 수신 자료를 추가 검증해야 한다. API 키 보유만으로 모든 서비스의 지역 적용이 완료되지는 않는다.

| 실제 지역 | 전체 행정경계 | 수록 공공공간 | 수록 범위의 의미 |
| --- | ---: | ---: | --- |
| 서구 `seogu` | 18개 행정동 | 58개 공간 | 기존 공개자료 패키지 |
| 순천 `suncheon` | 24개 읍면동 | 67개 공간 | 8개 읍면동에 수록. 원문 78행의 시간·요금별 조건을 같은 공간으로 통합 |

이 숫자는 회의실·강당 등을 포함한 **개방공간 단위**이며 건물 수, 최신 운영 여부 또는 예약 가능 공간 수가 아니다. 순천은 경계 전체를 수록하지만 공간자료가 없는 읍면동도 있다. 이를 실제 공간이 없거나 생활SOC가 부족하다는 근거로 해석하지 않는다. 순천의 기준일·출처·67개 공간 구성과 원문 보존 방법은 [순천 자료팩 설명](SUNCHEON_DATA.md)에 기록했다.

## 2. 메뉴 선택, API와 배포 기본 지역

메뉴 전환은 `/?region=suncheon`, `/?region=seogu` 주소로 이동하며 선택한 지역 자료를 다시 불러온다. 공개 선택 목록은 **`shared/region-catalog.js`의 `REGION_CATALOG`**에 등록되어 있다. 현재 허용하는 지역 ID는 `seogu`, `suncheon`이며 사용자가 임의 파일 경로나 전체 프로필을 보내 지역 설정을 바꿀 수 없다. 등록되지 않은 HTTP 지역 선택은 오류로 처리한다.

| 경로 | 지역 선택과 처리 |
| --- | --- |
| `/?region=suncheon` | 순천 메뉴·경계·공공공간·검토 흐름을 불러옴 |
| `GET /api/region-profile?region=suncheon` | 허용 목록의 순천 프로필과 공개 지역 목록 반환 |
| `GET /api/region-profile` | 서버 배포 기본 지역 프로필 반환 |
| `POST /api/ask` | JSON의 `regionId`로 등록 지역 선택. 순천은 순천 공개공간의 후보·출처·수록 범위에 근거해 조회 |
| `POST /api/space-review` | JSON의 `regionId`로 자료팩을 다시 읽고 해당 지역의 실제 공간 ID와 입력 조건을 검증한 뒤 계산·설명 |

브라우저가 보내는 `regionId`는 공개 등록 ID만 선택한다. 경계나 공간 원자료를 클라이언트가 임의로 바꿔 보내는 방식이 아니다. 두 POST 모두 화면이 현재 지역 ID를 명시하며, 서버는 해당 지역 자료와 공간 ID를 확인한다. 잘못된 지역·다른 지역 공간 ID·불일치하는 검토 조건은 혼합하지 않는다.

운영자는 서버 환경변수 `REGION_PROFILE`로 **아무 지역도 명시하지 않은 요청의 기본 지역**을 정할 수 있다. 지정하지 않으면 `seogu`다. 예를 들어 `REGION_PROFILE=my-city`이면 `public/data/regions/my-city.json`을 검증하여 기본 지역으로 읽는다. 별도 배포의 기본 지역 파일은 사용할 수 있지만, 앱의 공개 지역 선택에도 노출하려면 공개 목록에 등록해야 한다. 설정 파일이 없거나 잘못되면 오류를 알리고 임의로 서구 설정으로 돌아가지 않는다. 순천 메뉴를 선택할 때마다 환경변수나 배포를 바꿀 필요는 없다.

내부 지역 로더는 `server/region-profile.js`이며 기존 `api/ai.js` 라우터를 거친다. 별도 서버리스 함수를 추가하지 않는다. 공공공간 확인 기록·변경안과 입력 초안은 지역별로 구분한다. JSON 기록 가져오기도 현재 지역과 일치하는지 확인한다.

### 공개 프로필 규격

| 항목 | 용도와 작성 규칙 |
| --- | --- |
| `version` | 현재 `1` |
| `id` | 파일 이름과 같은 영문 소문자·숫자·하이픈 식별자. 예: `my-city` |
| `name`, `fullName` | 화면에 표시할 이름. 출처를 확인하여 운영자가 입력 |
| `jurisdictionCode`, `codeSystem` | 경계 자료의 지역코드와 코드 체계. 둘을 항상 함께 기록 |
| `timeZone` | 현재 지원 값은 `Asia/Seoul` |
| `bounds` | `[서쪽 경도, 남쪽 위도, 동쪽 경도, 북쪽 위도]` |
| `center` | 지도 중심 `[경도, 위도]`. 경계상자 내부 |
| `boundaryUrl` | 같은 사이트 `/data/` 아래 행정경계 JSON/GeoJSON |
| `facilitiesUrl` | 같은 사이트 `/data/` 아래 공공공간 JSON/GeoJSON |
| `facilityLayerId` | 공통 공공공간 화면은 `public-facilities` 사용 |
| `districtCount` | 행정경계 Feature 수와 일치하는 양의 정수 |
| `capabilities` | `spaceTwin`, `legacySeoguServices`를 각각 `true`/`false`로 지정 |
| `serviceCodes` | 별도로 확인한 제공기관별 코드. 현재 허용 키는 `taasSido`, `taasGugun` |
| `source` | 프로필 출처 `name`, `url`, 기준일 `asOf`, 선택 설명 `note` |
| `sample` | 합성 예시 여부. 운영 자료는 실제 출처를 확인한 후 `false` |

응답의 `layerMappings`는 공공공간 레이어 ID를 해당 URL과 사용 가능 여부에 연결한다. 프로필에서 생략하면 검증기가 생성한다. 직접 작성할 경우 `facilitiesUrl` 및 `capabilities.spaceTwin`과 일치해야 한다. 아직 연결하지 않은 자료가 있는 것처럼 표시하지 않는다.

서구의 `12240`과 순천의 `12150`은 수록 경계의 `adm_cd2` 앞 5자리로, **행정안전부 행정기관코드(`MOIS-ADM`)**로 표기한다. 원 제공자는 `adm_cd2`를 행정안전부의 10자리 행정기관코드로 설명한다. SGIS는 기하 경계의 원출처이며 이 코드의 체계와 구분한다. 기존 서구 TAAS 호출의 `29`/`140`, 순천 공공데이터 제공기관코드 `5790000`은 각각 별도로 보관하며 다른 서비스의 지역코드로 자동 대체하지 않는다. 코드 체계를 임의로 섞으면 화면은 정상이어도 다른 지역의 자료를 읽을 수 있다. [원 제공자의 속성 설명](https://github.com/vuski/admdongkor#속성의-adm_cd2)

API 키·비밀번호·비공개 URL은 공개 프로필에 넣지 않는다. 프로필 검증기는 허용하지 않은 키를 거부한다. 제공기관 인증키는 기존 서버 환경변수로 관리한다. 자료 경로는 `/data/...json` 또는 `/data/...geojson`으로 제한하며 외부 URL, 경로 이동, 인코딩된 경로, 쿼리·해시를 허용하지 않는다. 출처 URL은 표시용으로만 보관하며 프로필 로더가 접속하지 않는다.

## 3. 새 지역의 자료 패키지 준비

한 폴더에 다음 세 파일을 준비한다.

- `manifest.json`: 위 규격의 지역 프로필
- `admin-boundaries.geojson`: 행정동·읍면동 등의 Polygon 또는 MultiPolygon
- `facilities.geojson`: 공공공간의 Point 목록

`public/data/regions/adoption-template.json`은 프로필 구조를 보여 주는 템플릿이다. 표시 이름, 코드, 좌표는 **합성 예시**이며 해당 경계·시설 파일은 배포 자료에 포함하지 않았다. 그대로 복사하여 운영하는 프로필이 아니다. 지역명만 바꾸지 말고 실제 경계·공공공간·출처·코드 체계를 함께 교체해야 한다.

### 좌표와 식별자

GeoJSON 좌표는 WGS84의 `[경도, 위도]` 순서로 준비한다. 국내 투영좌표를 쓴 원자료는 수집 과정에서 변환하고 변환 이력을 남긴다. CRS를 생략한 표준 GeoJSON 또는 명시적인 EPSG:4326/CRS84를 허용한다. 고도까지 들어 있는 3차원 좌표는 현재 검증 규격에서 제외한다.

행정경계의 각 Feature는 고유한 `properties.dongId`와 `dongName`을 갖는다. `labelPoint`가 있으면 해당 행정경계 안의 `[경도, 위도]`여야 한다. 링은 닫혀 있어야 하고 면적이 있어야 한다. 모든 경계 좌표가 프로필의 `bounds` 안에 들어가야 한다.

공공공간은 `properties.id` 또는 `feature.id`에 **변하지 않는 문자열 식별자**를 둔다. 두 곳에 쓰면 값이 같아야 한다. 원자료에 영구 시설·공간 ID가 있으면 이를 우선 사용하며 순번·화면 정렬·날짜로 ID를 바꾸지 않는다. 같은 건물의 두 회의실은 서로 다른 공간 ID를 사용한다. 영구 공간 ID를 제공하지 않는 순천 표준데이터는 별도 ID 연결표를 유지한다. 날짜·운영시간·요금이 바뀌어도 ID를 유지하며 공간명·주소 변경은 담당자 대조 후 기존 ID에 연결한다. ID가 달라지면 기존 확인기록과 연결이 끊어질 수 있다. 자세한 처리와 한계는 [순천 자료팩 설명](SUNCHEON_DATA.md)을 따른다.

공공공간의 필수 속성은 ID와 `properties.name`이다. 좌표는 경계상자뿐 아니라 실제 행정경계 안에 있어야 한다. `dongId`를 넣으면 경계의 ID와 일치하고 좌표도 해당 동에 있어야 한다. `dongId`를 모르면 생략할 수 있으나 검증 결과에 경고가 남는다. 위치를 모르는 시설에 임의의 동 중심점을 넣지 않는다.

### 출처와 시점

두 GeoJSON의 최상위 `metadata`에 최소한 `sourceName`, `sourceUrl`을 기록한다. 자료 기준일 `sourceDate`, 기준일 범위 `sourceDateRange`, 수집시각 `retrievedAt`을 구분한다. 날짜는 실제 달력에 있는 `YYYY-MM-DD` 값이어야 하며 기준일 범위의 시작은 끝보다 늦을 수 없다. 수집시각은 ISO 8601 형식을 권장한다.

```json
{
  "type": "FeatureCollection",
  "metadata": {
    "sourceName": "실제 공개자료의 이름과 제공기관",
    "sourceUrl": "https://example.org/replace-with-real-source",
    "sourceDate": null,
    "retrievedAt": "2026-10-22T00:00:00Z"
  },
  "features": []
}
```

위 주소와 시각은 형식 설명용이다. 실제 자료로 교체한다. 기준일을 모르면 `null`로 두고 갱신 필요 항목으로 관리한다. 수집한 날짜를 원자료의 기준일인 것처럼 넣지 않는다. 시설별 출처와 기준일이 다르면 `properties.sourceName`, `sourceUrl`, `sourceDate`에 기록한다. 현재 검증기는 개별 기준일이 없는 공간을 별도로 경고하므로 전체 자료 기준일과 구분해서 점검할 수 있다.

사용허가·공공누리 등 이용조건, 관리부서, 원본 URL, 변환 방법도 수집 기록에 남긴다. 검증기는 출처 이름과 주소의 형식을 확인할 뿐 실제 이용허락이나 원자료의 진위를 인증하지 않는다.

운영시간·휴관·무장애 접근·예약·정원·이용료 등은 확인한 범위만 기록한다. 빈값은 폐쇄, 무료, 수용인원 0으로 바꾸지 않는다. 게시된 운영시간이 있더라도 해당 날짜의 개방이나 예약 가능성을 확정하는 근거가 되는지는 따로 확인한다. 원본 공개자료와 담당자가 확인한 상태, 검토용 가정을 구분해 보관한다.

## 4. 검사하고 연결하는 순서

1. 대상 지자체의 공개자료를 수집·변환하여 세 파일을 준비한다. `manifest.json`의 두 URL은 `/data/regions/my-city/admin-boundaries.geojson`과 `/data/regions/my-city/facilities.geojson`처럼 실제 배포 경로를 가리키게 한다.
2. 프로젝트 루트에서 `node scripts/validate-region.mjs /absolute/path/to/region-pack`을 실행한다. 오류는 고치고, 경고는 기준일·행정구역·자료 공백의 의미를 검토한다. 파일을 자동 보정하거나 외부로 전송하지 않는다.
3. 검증한 `manifest.json`을 `public/data/regions/my-city.json`으로 복사한다. 경계·시설 파일은 프로필에 적은 경로에 둔다. 기존 서구 파일을 덮어쓸 필요가 없다.
4. `node scripts/validate-region.mjs --profile my-city`로 배포 폴더 전체를 다시 검사한다. 기본 자료는 `--profile seogu`로 검사한다. 운영 프로필은 `sample: false`여야 하며, 합성 예시가 들어 있으면 적용을 중단한다.
5. 앱 메뉴에서 선택하게 할 지역이면 `shared/region-catalog.js`의 `REGION_CATALOG`에 ID·이름·전체 이름·기능 범위를 등록하고 빌드·배포한다. 한 지역 전용 배포의 기본 지역만 바꿀 때는 `REGION_PROFILE=my-city`를 사용한다. 기존 등록 지역을 메뉴에서 선택하는 데는 새 배포나 환경변수 변경이 필요하지 않다. 별도 제공기관 API 키가 필요한 기능은 서버 환경변수로 관리한다.
6. `/?region=my-city`, `/api/region-profile?region=my-city`의 ID·이름·경계·자료 URL을 확인한다. 화면의 읍면동 개수, 지도 중심, 공공공간 선택, 시나리오 결과, `POST /api/ask`와 `POST /api/space-review`의 `regionId`·출처를 실제 표본과 대조한다. 기존 서구 자료가 새 지역의 정보로 노출되지 않는지, 수록 범위 밖 질문을 실제 자료 부재로 단정하지 않는지도 확인한다.
7. 운영 전 담당 부서가 주요 공간의 위치·상태·연락처·기준일을 표본 확인하고, 자료 갱신 책임자와 점검 주기를 정한다.

새 지역을 목록에 추가하고 배포하는 것은 운영 작업이다. 검증 CLI 자체는 배포하거나 서버 설정을 수정하지 않는다. 이미 등록된 순천을 사용하려면 메뉴에서 **다른 지역도 적용해보기 → 순천 적용해보기**를 선택하면 된다.

검증기가 검사하는 항목은 프로필 필드, 코드 체계의 존재, 안전한 경로, 자료 크기, 날짜 형식, 중복 ID, 좌표계, 경계 개수, 닫힌 링, 0이 아닌 링 면적, 범위 포함, 동 매핑이다. 행정경계의 모든 위상 오류·자기 교차·동 사이 중첩을 판정하는 GIS 전문 검사는 아니다. 출처의 진위, 최신 운영상태, 실제 현장 정확성도 담당자 확인이 필요하다. 현재 제한은 행정경계 3,000개, 공공공간 5,000개, 경계 좌표 2,000,000개, 자료 파일당 32MiB다. 이 상한은 화면·계산의 성능 보장을 의미하지 않으므로 큰 지역은 별도 성능 검증을 한다.

## 5. 확인된 실제 재사용성과 아직 필요한 업무 실증

서구와 순천의 실제 자료팩을 동일한 `validateRegionDataPack`, 지역 로더, `seedAssets`, 공공공간 비교 엔진으로 처리한다. 서구는 18개 행정동·58개 공간, 순천은 24개 읍면동·67개 공간으로 구조·식별자·경계 포함 검사를 통과했다. 순천의 67개 공간은 8개 읍면동에 수록되어 있으며, 같은 좌표의 여러 공간을 건물 하나씩으로 해석하지 않는다.

`tests/suncheon-data.test.mjs`는 실제 순천 자료로 다음을 회귀 검사한다.

- 2026-07-01 원본 경계 도형 불변과 24개 내부 라벨점.
- 78개 보존 원문 행과 표시되는 67개 공간의 명칭·좌표·출처 기준일 일치.
- 8개 공간의 복수 시간·요금 조건 보존, 20개 서로 다른 대표좌표, 8개 읍면동의 수록 범위.
- 내부 ID 연결표와 공간 식별자 일치.
- 공개 운영시간으로 현장확인 기록을 생성하지 않으며 실제 비교 엔진에서 초기 67개 공간이 모두 미확인으로 남는 동작.

기존 `tests/region-profile.test.mjs`의 별도 **합성 지역**은 오류·경로·시연자료 차단 검사를 위한 시험 입력으로 계속 사용한다. 합성 자료의 검사와 실제 순천 자료 교체 검증을 혼동하지 않는다. 외부 URL·경로 이동·폴더 밖 심볼릭 링크 차단, 지역코드 혼용 방지, 좌표 및 식별자 오류도 공통 검증 범위다.

이는 **공개자료를 사용한 두 실제 지역의 기술 적용 검증**이다. 실제 지방공무원의 업무 성과를 입증하려면 담당자 확인, 같은 과제·자료·완료기준에서의 처리시간·오류율·누락률 비교, 결과물 검토가 추가로 필요하다. 기록을 입력하지 않은 상태에서 개선율을 만들어 표시하거나 임의로 대회 점수의 상승 근거로 삼지 않는다.

확산 설명은 다음과 같이 제시할 수 있다.

> 공공 API와 지자체 공개자료를 같은 구조로 정리하고, 지역 경계·코드·출처 설정을 교체해 재사용하도록 구성했습니다. 서구 18개 행정동·58개 공공공간과 순천 24개 읍면동·67개 공개공간을 같은 앱에서 선택하고 조회·검토할 수 있습니다. 순천의 공간 자료는 8개 읍면동 수록 범위이며 원자료와 현장 확인값, 변경 가정을 구분합니다. 다음 단계로 지자체 담당자가 실제 과제를 수행해 처리시간과 오류·누락의 변화를 측정합니다.

## 6. 운영과 추가 확장

자료를 갱신할 때는 이전 파일과 비교해 삭제·추가·이름 변경·좌표 이동을 검토하고, ID를 유지한 채 검증 CLI를 다시 실행한다. 기준일과 수집시각을 함께 갱신하고 출처를 보존한다. 시설이 자료에서 사라졌다는 이유만으로 폐쇄로 간주하지 않는다. 담당자 확인 상태의 만료나 재확인 여부는 해당 상태의 시점에 따라 판단한다.

현재 공공공간 확인 기록·변경안은 이 브라우저에 지역별로 저장하고 JSON 내보내기·가져오기로 보관한다. 지역 프로필을 바꾸는 것만으로 다중 사용자 권한, 부서 공동저장, 결재, 변경 이력의 서버 보관이 생기지 않는다. 부서 공동 운영에는 접근권한, 자료 수정 책임, 승인·감사 이력, 백업과 복구를 추가해야 한다.

기존 서비스까지 확장할 때는 서비스별 어댑터 목록에 `provider`, 지역코드 체계, 지역 매개변수, 관측소·격자, 사용 가능 여부, 기준시점 정책을 명시하고 단위별 계약 테스트를 둔다. 서구 상수에 의존하는 코드를 하나씩 이 설정으로 옮긴 뒤에만 해당 기능을 새 지역에서 활성화한다. 같은 화면을 재사용하더라도 자료가 없는 분야에는 미수집·미연결 상태를 분명하게 표시한다.
