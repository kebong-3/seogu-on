Android는 조작 대상의 충분한 크기와 의미 있는 설명을 권고하며, 해당 문서는 48dp 크기를 예로 든다. 이 앱의 웹 CSS 픽셀과 Android의 dp가 모든 기기에서 물리적으로 같다는 뜻은 아니다. 코드상의 최소 크기와 실제 기기 조작을 별도로 검증해야 한다. [Android: Make apps more accessible](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views)

NIST는 디지털트윈의 실제 대상 표현·상태 변화와 신뢰 문제, 모형의 개발·검증·유지관리를 다룬다. 여기에서 도출한 **우리 앱의 검토 원칙**은 공개자료·관측·계산·사용자 가정의 출처와 시각을 구분하고, 실제 상태 갱신과 가상 비교를 섞지 않는 것이다. NIST가 서구온을 평가하거나 인증한 것은 아니다. [NIST IR 8356](https://csrc.nist.gov/pubs/ir/8356/final), [NIST Digital twins](https://www.nist.gov/digital-twins)

## 2. 사용자 관점의 핵심 판단

기능은 상당히 갖춰졌지만, 주민이 한 번에 판단해야 하는 항목이 많다. 지역 선택·AI 질문·시설 종류·서비스·지도 방식·행정 도구가 같은 화면에서 경쟁한다. 주민에게 필요한 첫 질문은 “어느 동에서 무엇을 하려는가”이며, 담당자에게 필요한 첫 질문은 “어떤 과제를 어떤 근거로 검토하는가”다. 이 두 흐름을 구분해야 한다.

지도와 시설 목록, AI 방문계획, 실제 경로, 현장조치가 각각 존재하는 것은 장점이다. 그러나 사용자가 다음 기능을 다시 찾아 들어가야 하는 지점이 남아 있다. 기능 메뉴의 수를 늘리기보다 **시설 선택 → 이용조건 확인 → 목적지로 사용 → 경로 확인**을 연결해야 한다. AI는 이 흐름의 입력을 돕고, 모호한 대상이나 근거 없는 조건은 확인 대상으로 남겨야 한다.

주의문을 많이 쓰는 것만으로 오해가 줄지는 않는다. 중요한 한계는 행동 바로 옆에 짧게 표시하고, 원자료·계산 방법은 펼쳐 볼 수 있어야 한다. 실제 확인된 시설 상태, 예전 공개자료, 계산 결과, 사용자의 폐쇄·개방 가정이 화면에서 즉시 구별되지 않으면 보기 좋은 3D 화면이 오히려 과도한 확신을 줄 수 있다.

## 3. 개선 전 6개 관점의 모의 점수

## 4. 새 UX·디지털트윈 피드백 40개

`구현`은 지금 코드로 개선 가능한 항목, `혼합`은 구현 후 실제 이용자·기기 확인이 필요한 항목, `현장`은 현장·기관 자료 없이 완료할 수 없는 항목이다. P1은 이번 핵심 흐름, P2는 일관성·지원 개선을 뜻한다. 아래 표의 수용 기준은 **앞으로 확인할 기준**이며 이미 통과한 결과가 아니다. 실제 결함을 확인한 항목과 사용성 위험에 대한 개선 가설을 구별하여 적었다.

## 5. 구현에서 지킬 선

주민 기본 흐름은 **지역 선택 → 필요한 서비스 → 다음 행동**이다. 생활지도는 시설 종류와 목록을 먼저, 도보는 출도착과 실제 조회를 먼저, 재난은 자료의 시점·종류와 확인 행동을 먼저 보여 준다. 행정 검토는 별도 진입점에서 현장 과제·대안 비교·자료 점검을 연다. 같은 원자료와 실제 기능은 보존하고 초기 노출과 연결 순서를 바꾼다.

디지털트윈 설명은 다음 네 의미를 섞지 않는다.

| 화면 의미 | 필요한 근거 | 허용하지 않는 해석 |
| --- | --- | --- |
| 공개자료 | 제공기관·원자료·가능한 기준일 | 공개 목록에 있다는 이유만으로 지금 개방·예약 가능 |
| 현장 확인 | 확인 시각·대상·근거·유효 범위 | 개인 입력이라는 이유만으로 기관의 공식 확인·승인 |
| 계산 참고 | 입력 시각·자료·모형·계산 범위·미평가 영역 | 그늘 근사나 과거 관리지점을 실제 현재 안전·결빙 보증으로 사용 |
| 내 가정 | 사용자가 바꾼 조건과 비교 기준 | 임시 폐쇄·개방 가정을 실제 상태나 정책 효과로 전파 |

시설 수 A/B의 계산 대상은 개인 과제에 기록한 시설 집합임을 유지한다. 수가 늘었다는 이유로 수요 충족·위험 감소·보행 편익을 만들어 내지 않는다. 기관 공동 저장·인증·권한·승인 서버와 현재 운영·관측 자료는 이번 화면 개편만으로 구현된다고 적지 않는다.

## 6. 구현 후 재평가 방법 — 아직 미실행

1. 수정된 화면·소스·자동검사·브라우저 관찰을 UX01–UX40에 연결한다. ‘구현’, ‘일부’, ‘미반영’, ‘현장 필요’를 구별하고 실패도 남긴다.
2. 지역 선택→생활 시설 찾기→목적지 적용→현재 출발 경로 조회, 검색 실패 후 복구, 모바일 지도찍기 취소, 키보드 상세 열기·닫기, 개인 기록과 가정 비교를 같은 조건으로 확인한다.
3. 여섯 관점의 같은 배점으로 다시 평가한다. 화면 개선으로 확인된 항목만 반영하고 실사용자·공식 자료·기관 도입의 미검증 항목은 남긴다. 새 디자인이라는 이유로 창의성·확산성을 자동 가산하지 않는다.
4. 실제 기기·주민 관찰과 현장 자료 확보 후에는 그 증거를 별도 후속 평가로 추가한다. 이번 개발자의 화면 검사를 실제 주민 실증으로 표시하지 않는다.

개선 전 평균 67.5점은 위 방법으로 후속 비교할 모의 기준점이며 앞으로의 점수를 예고한 값이 아니다.

## 7. 구현 후 항목별 대조

아래의 `구현`은 해당 화면·동작이 코드에 있다는 뜻이다. 실사용자에게 쉽다는 실증, 모든 기기의 접근성 통과, 현재 시설 운영·안전 보증은 아니다. `부분`은 핵심 개선은 있으나 제안 전체의 범위를 충족하지 못한 경우다. `현장 필요`는 코드만으로 완료할 수 없는 항목이다.

최종 항목 집계는 **구현 26개·부분 10개·현장 필요 4개**다. 이는 40개 UX 검토 항목의 상태 분류이며 앱 전체 완성률이나 현장 효과의 측정값이 아니다.

## 8. 우선할 후속 변경

1. **실제 상태와 가정의 공통 표시**: 객체별 원자료 기준일·현장 확인일·유효기간·공식/개인 근거를 연결한다. 일반적인 ‘자료·가정 안내’만으로 각 핀의 현재 상태가 검증되는 것은 아니다.
2. **남은 메뉴와 조건 요약**: 행정 도구의 중복 진입, 보조 서비스의 현재 위치 표시, 경유·체류·우회 조건 요약을 정리한다. 과제마다 새로운 입력창을 추가하는 방향을 피한다.
3. **실기기 접근성과 처음 이용자 관찰**: 실제 작은 화면·큰 글씨·화면읽기로 같은 과제를 수행하고, 중단·오선택·되돌아가기와 그 이유를 기록한다. 개발자 브라우저 검사를 주민 실증과 합산하지 않는다.
4. **공식 운영 근거와 책임**: 현재 운영·출입구·귀갓길·노면 자료의 담당자와 주기를 확정한 뒤 실제 반영 사례를 남긴다. 그 전에는 현재 안전·무장애·실시간 운영 트윈을 보장하지 않는다.

## 9. 구현 후 모의 재평가

재평가 근거는 위 소스 대조와 독립 표적 검사 **77개 통과·실패 0개**, 개인 기록·측정 관련 기존 회귀 **46개 통과·실패 0개**다. 77개는 R·L·W 네 시험 파일을 함께 실행한 결과이며, 46개는 F의 모형·화면·측정 세 파일을 실행한 결과다. 수정 후 의미 있는 취소·초점·지연 응답 조건과 날짜 구분, 계절 결과의 접히지 않는 기준시각 표시를 확인했다. 전체 통합검사는 통합 담당자가 수행하며 이 수치와 중복 합산하지 않는다.
